# Description

After the scx submodule bump to upstream dd06cd27 (sync-upstream/20260622), test_bug1_canonical_subprocess_reproduces_throttle deterministically yields is_throttled==1 at end-of-run instead of the V4-C-era expectation is_throttled==0. Throttle enforcement still works (5/6 periods, nr_throttled_tasks=4) and the determinism sibling test passes, so this is NOT flakiness. Upstream substantially rewrote cgroup_bw: 776ae41e (cgrp pointer -> u64 cgrp_id + taskc per-task cache), arena migration (4fa7fb81/48757ded), a52f85e3 (root cgroup via loader task), 58740f71 (period_budget poisoning fix via remote-rq detection in update_stat_for_running), 6c4df643 (throttle-check consolidation). The 58740f71 stall fix targets phantom runtime from stale per-CPU rq->clock_task on remote-rq ops.running — a mechanism scxsim does NOT reproduce (it charges consumed_ns directly via engine-driven scx_cgroup_bw_consume). Task: determine whether is_throttled==1 at end is genuinely-correct new upstream behavior (update assertion) or a scxsim port/accounting gap vs the new period_budget semantics (fix engine). Test is currently #[ignore]'d with a pointer to this issue. Context: tg update-scx-submod-v6 / sync-upstream/20260622.

# Notes

PREMISE CHANGED — the binary question as posed can no longer be answered as posed, and that is itself the finding.

This issue records that after the 2026-06-22 cgroup_bw rewrite the test 'deterministically yields
is_throttled==1', explicitly NOT flakiness, and asks: (a) correct new upstream behaviour, update the
assertion, or (b) a scxsim accounting gap, fix the engine.

As of 2026-08-12 that premise no longer holds. Measured today at integration:
    this dev box: is_throttled 0, nr_throttled_tasks 0   -> the test PASSES
    GitHub CI:    is_throttled 1, nr_throttled_tasks 4   -> the test FAILS
Same commit, same fixture, same --cpus 4 / --duration 600ms / --watchdog 200ms.

So it is no longer deterministically 1 everywhere; it is 0 here and 1 there. Neither (a) nor (b) is
right on its own: if is_throttled==1 were simply correct post-rewrite behaviour it would be 1 on this
box too, and if it were purely an engine accounting gap it would be 1 in both places as well. The
value now depends on the environment, which is a third thing neither branch of the question covers.

WHAT CHANGED IN BETWEEN is worth noting for whoever picks this up: integration 37f7f8a fixed
check_watchdog reporting deliberate cgroup-bandwidth throttling as starvation (exit 42). That fix
altered the run's trajectory — the run no longer aborts early — so the end-of-run throttle state this
issue is about is not the same measurement it was in June.

RULED OUT LOCALLY BY EXPERIMENT: host CPU count (316 / 4 / 2 via taskset), ASLR (on and off, 5 runs
each), and repetition (20 consecutive runs). All give 0. Remaining hypothesis is toolchain codegen —
CI uses rustc 1.97.1 with Ubuntu clang, this box rustc 1.96.0 with clang 18.1.8 — which would put it in
the same family as mb sim-hyr11. Not confirmed.

Tracked in parallel as mb sim-1ei8j, filed from the CI side. These two issues are the same underlying
question seen from two directions; whoever takes one should read both. Note that sim-1ei8j's original
'garbage pointer values' evidence has been retracted — that was an upstream printf arity bug in one
dump line (cgroup_bw.bpf.c:2907, five numeric conversions against three arguments), diagnostic-only,
and it does not touch is_throttled.

The test remains #[ignore]d with a live issue reference, which is an honest record of an open question
rather than a silent skip. It is not blocking integration.
