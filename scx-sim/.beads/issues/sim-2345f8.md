# Description

Repro (tg write-cosmos-tests): cosmos, 2 CPUs, 6 non-yielding CPU-bound tasks (Run Forever), cpu_util_map forced busy (util=1024, busy_threshold=512) so is_cpu_busy()=true. At t=0 two tasks grab local DSQs; the other four bounce to the shared DSQ (DSQ 0) via cosmos_enqueue's deadline path (task_dl/scx_bpf_dsq_insert_vtime). Observed: only the two initially-local tasks run (~199ms of 200ms each); the four shared-DSQ tasks get 0 runtime — even with cosmos_set_time_preemption(true). Expected: kernel enforces slice expiry -> cosmos_dispatch consumes shared DSQ (scx_bpf_dsq_move_to_local(0)) -> rotation. So either (a) ticks/slice-expiry don't re-dispatch a running non-yielding task on this path, or (b) move_to_local(SHARED_DSQ=0) isn't consuming. The round-robin (not-busy, local-DSQ) path rotates fine (generic test_multiple_tasks_single_cpu passes), so the gap is specific to shared-DSQ consumption / slice-preemption of a running task when competitors sit only in the shared DSQ. Workaround in test_busy_deadline_mode: bursty (Run+Sleep) tasks yield voluntarily. Investigate slice-expiry re-dispatch + shared-DSQ consume under busy mode.
