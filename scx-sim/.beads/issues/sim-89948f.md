# Description

## Problem

A CPU-bound task that is RUNNABLE-BUT-QUEUED (contended) at the moment of `cgroup_migrate` under the mitosis scheduler is STRANDED after the migration: it is never scheduled again, its runtime freezes, while co-resident tasks keep running. This is the exact scenario sim-03229 described ("bug only manifests when migration happens while the task is already queued") — that issue is CLOSED and `handle_cgroup_migrate` has re-enqueue logic (engine.rs ~3105), but the stranding still reproduces for mitosis, so the fix is incomplete or regressed for the mitosis/cpu_controller_disabled path.

## Repro (deterministic, integration@0b3f491, scx submodule 59c30bae)

4 CPUs, cell_a cpuset {0,1}, cell_b cpuset {2,3}. 8 forever CPU-bound tasks all in cell_a (oversubscribed, so pid=1 is frequently queued). `cgroup_migrate(Pid(1), cell_a, cell_b, 150ms)`, duration 400ms, watchdog disabled.

Observed: pid=1 sched_count pre[0-150ms]=18, post[150-400ms]=0. total_runtime frozen at 75.6ms. Last lifecycle event for pid=1 is TaskScheduled @146.3ms (just before migration). Bystanders (pid 2-8) keep running. exit=Normal (no watchdog since 250ms << 30s default).

The NON-contended case (task has its own idle CPU, never queued) does NOT strand — the migrant keeps running on its CPU across the migration.

## Likely root cause (needs confirmation)

For mitosis `cpu_controller_disabled=true` (set in scx-sim/schedulers/mitosis/wrapper.c:502), `mitosis_cgroup_move` returns early (mitosis.bpf.c:1228) so tctx->cell/dsq are unchanged; the engine dequeues+re-enqueues, but the re-enqueue path apparently does not place the queued task back onto a DSQ that a CPU consumes. Interaction of engine re-enqueue with maybe_refresh_cell / cell-0 DSQ routing under cpu_controller_disabled.

## Impact

Blocks writing a passing 'cell-to-cell task migration under load' test (tg test-mitosis-cell-migration). A guard test asserting the correct behavior (queued migrant keeps progressing) is added #[ignore]'d referencing this issue.
