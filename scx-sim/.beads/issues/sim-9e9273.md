# Description

Discovered while writing cgroup_bw_throttle_unthrottle.rs (tg test-cgroup-bw-throttle-unthrottle).

Observation (LAVD, enable_cpu_bw=true, deterministic serial engine):
- When a cpu.max limit sits on the cgroup that DIRECTLY holds the running task, throttle/unthrottle works: CgroupBwReplenish shows runtime_total_last>0, the cgroup throttles at quota and unthrottles at the period boundary (verified for a flat cgroup AND a nested child via cgroup_nested_bw: both give 8 alternating CbwThrottleCgroups transitions, rtl ~92ms/16ms/12ms).
- When the limit sits on an ANCESTOR and the task lives in an unlimited DESCENDANT, the ancestor's CgroupBwReplenish shows runtime_total_last=0 and it NEVER throttles: the descendant CPU runtime is not propagated up to the limited ancestor's cgroup_bw accounting. The descendant runs ~558ms/600ms essentially unthrottled.

Repro (4 cpus): cgroup_with_bandwidth('lim_parent',..,100000,10000,0); cgroup_nested('lim_child','lim_parent',None); add_task_in_cgroup('deep',..,'lim_child') -> REPL cgid=lim_parent kt=false rtl=0 (never throttles).

Contrast: tests/cgroup_hierarchy.rs::test_bandwidth_enforced_across_deep_hierarchy_lavd asserts ancestor-limit enforcement and PASSES, but runs WITHOUT enable_cpu_bw via the engine admission gate (is_cgroup_throttled) -- a different path than the enable_cpu_bw replenish/BTQ path.

Expected (kernel fidelity): the kernel charges a descendant CPU runtime against every bandwidth-limited ancestor, so an ancestor cpu.max should throttle nested tasks under enable_cpu_bw too.

Impact: the new cgroup_bw_throttle_unthrottle.rs nested test therefore puts the limit on the nested child (which directly holds the task); ancestor-limit throttling under enable_cpu_bw is deferred here. Investigate the scx_cgroup_bw_consume charge call site and whether it walks cgroup ancestry vs. the library hierarchical roll-up in cgroup_bw.bpf.c.
