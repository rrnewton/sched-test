# Description

The Rust coverage ratchet fails on GitHub CI for scx_perf and only for scx_perf:

  FAIL: Rust library coverage ratchet:
    scx_perf: coverage 32.3% < baseline 78.4% (floor 77.9%)
    scx_simulator: 74.8% (baseline 73.5%)   <- fine
    scxsim-build:  58.5% (baseline 51.9%)   <- fine

ATTRIBUTION IS SETTLED. Reproduced on ci/coverage-gate-runner-disk = integration + ONE CI-only commit, zero scx-sim source (run 31651876396, scx_perf 32.3%), and on feat/layered-support (32.5%). Same failure, ~0.2pp apart, so it is a property of the CI environment, not of either branch.

WHY IT IS ONLY SURFACING NOW: integration's simulator job had never reached the ratchet. It died first on missing cargo-llvm-cov, then on runner disk exhaustion (PR #87). The baseline in data/rust_coverage_baseline.csv was therefore recorded from DEV-HOST runs and has never been met by CI.

LIKELY CAUSE: scx_perf is the PMU crate. Its coverage almost certainly comes from tests that need a real perf_event counter, which a GitHub runner does not provide (no PMU / perf_event_paranoid). Those tests skip or bail early on CI, so over half the crate never executes. 78% -> 32% is the shape of 'the hardware-dependent half did not run', not of a regression.

WHY IT MATTERS: the ratchet hard-fails, so while this stands NO PR can show a green simulator job, and the whole no-silent-skips effort is undermined by a gate that cannot pass in the environment that enforces it.

FIX OPTIONS, in preference order:
1. Make the PMU-dependent scx_perf tests run on CI (a software counter fallback, or PERF_COUNT_SW_*), so the number is real in both places.
2. If they genuinely cannot run, record a SEPARATE CI baseline for scx_perf rather than lowering the shared one — lowering it to 32% would silently forfeit the dev-host coverage the crate actually has.
3. Do NOT simply run --update-baseline from a CI run. That bakes the degraded environment in as the standard and is the false-pass this gate exists to prevent.
