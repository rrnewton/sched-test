# scx#3618 as a CLI invocation

A command anyone can run, rather than Rust that builds a `Scenario`. Workload:
`scx-sim/examples/scx3618_cpumax_unbounded_wait.json`.

## The command

```bash
printf '[scheduler.bool_globals]\nenable_cpu_bw = true\n' > /tmp/lavd_cpubw.toml

SCX_SIM_NOISE=0 scxsim run -s lavd \
  --config /tmp/lavd_cpubw.toml \
  --watchdog-timeout 30s \
  examples/scx3618_cpumax_unbounded_wait.json
```

Result, **without** the patch:

```
  Logical time elapsed:   40.3s
scxsim: ExitKind::ErrorStall pid=2 runnable_for_ns=40179349812
```

**With** scx#3618 applied (`cd scx && git apply -3 pr3618.diff && cd ../scx-sim
&& make rebuild-schedulers`), the *same command*:

```
  Logical time elapsed:   40.3s
scxsim: ExitKind::ErrorStall pid=2 runnable_for_ns=40179349812
```

Byte-identical. The wait is **40.18s** in both cases — against a fix whose
stated aim is a ~4s bound. This is the before/after, and it is a one-line
difference in the build rather than a code diff.

The workload is faithful to the Rust repro: a `/tight` cgroup at
`cpu.max = "125 100000"` (125µs per 100ms) holding one compute hog and eight
repeatedly-waking 200µs/1000µs victims, plus an unlimited `competitor` in the
root cgroup. Throttling is confirmed engaged from the CLI's own output —
`quota: 125000/100000000`, `is_throttled: 1`, `nr_throttled_periods: 2399/2400`,
`nr_throttled_tasks: 7`.

## `SCX_SIM_NOISE=0` is load-bearing, and that is a finding

The same command **without** it runs the full 240s and never stalls. The Rust
repro used `.instant_timing()`, which disables noise; carrying that over to the
CLI is what makes it reproduce.

So **the pathology is noise-fragile**: 20% run-jitter is enough to prevent the
specific starvation ordering. That is worth knowing and was invisible while the
repro lived in Rust with noise implicitly off. Two readings, and I cannot
currently choose between them:

- the starvation needs a deterministic ordering that jitter perturbs, in which
  case production — which has noise — may hit it more rarely than the repro
  suggests; or
- 240s is simply too short to catch a noisier, less regular version of the same
  effect, in which case a longer window would show it.

Given tonight's history with window ceilings, the second should be tested
before anyone leans on the first.

## Threshold

`--watchdog-timeout 30s`, chosen for fidelity to scx#3618's own claim, which is
specifically about *the 30-second* runnable-task-stall watchdog. **Report the
wait — 40.18s — not "the watchdog fired".** The trip is a parameter; the wait is
not. For sweeping, `4s` is cheaper and preserves the gradient (measured
separately: 4.98 / 9.98 / 40.28 against 4.98 / 10.98 / 40.28 at 30s).

## A trap found on the way, worth fixing separately

`global.duration` is parsed with `as_i64()` (`safe/rtapp.rs:677`). **A float is
silently ignored and replaced by the 10-second default.** My first attempt used
`240.0` and ran for 10s, which looked exactly like "the CLI does not reproduce
it". The shipped `examples/cgroup_throttling.json` declares `"duration": 0.3`
and therefore also runs for 10s rather than 0.3s. Silent, and it produces a
window ceiling — the same failure mode that generated two wrong verdicts in this
investigation already.

## Correction: it was never noise. It is context-switch overhead.

The claim above that `SCX_SIM_NOISE=0` is load-bearing is **wrong**, and the
question "does noise mask the pathology or prevent it" has the answer
**neither**. Measured in the Rust harness where noise and overhead can be set
independently, 240s window, quota 125µs/100ms:

| overhead | noise CV | worst wait |
|---|---|---|
| off | 0% | 42.18s |
| off | 20% | 42.18s |
| on | 0% | **9.30s** |
| on | 20% | **8.80s** |

**Noise changes almost nothing** — 42.18 against 42.18, and 9.30 against 8.80,
a ≤5% effect. **Context-switch overhead changes everything** — a 4.5x reduction
in the worst wait. Two supporting sweeps agree: at overhead-off the wait is
42.18s at every noise level from 0% to 20% (0/1/5/10/20% CV all large), and it
is 42.18s at 60s, 240s and 960s windows, so it is converged rather than
window-limited.

**Why the misattribution happened.** `instant_timing()` is
`noise(false).overhead(false)` — *two* switches, not one. The Rust repro called
it, so both were off. When the CLI reproduced only with `SCX_SIM_NOISE=0` I
attributed the difference to the one knob I had named, without checking the
other. Classic single-variable inference across a two-variable change.

**Why the CLI behaved as it did**, at least in part: with overhead on the wait
is ~9s, and the CLI ran a **30s** watchdog. A 9s wait does not trip a 30s
watchdog, so "noise on → no stall" is really "9s < 30s". That reconciles the
no-stall case. It does **not** fully reconcile the `SCX_SIM_NOISE=0` case
tripping at 40.18s with overhead nominally on — either that env var reaches
more than `NoiseConfig` on the rt-app path, or the rt-app path differs from the
builder path in some other way. **Unresolved, and stated as such.**

### What this means for the finding

It **strengthens** it. The pathology does not depend on a noiseless simulator,
which was the reading that would have weakened or killed it. It survives full
20% run-jitter at essentially unchanged magnitude. The prior noise research
predicted this: a worst-case wait is an *extreme*, not a mean, so it is not
subject to the `1/sqrt(N)` averaging that makes per-cgroup CPU time immune to
symmetric noise — and indeed noise neither averages it away nor creates it.

The real sensitivity is to context-switch overhead, which is a *modelling*
parameter rather than a realism one: 500ns voluntary / 1000ns involuntary are
scxsim constants, and whether production values are higher or lower is a
separate question. Reported waits should say which setting was used. Every
number in this investigation before this correction was measured with overhead
**off**, so the 1.98 / 4.98 / 10.98 / 21.18 / 40.28 / 81.18 gradient is the
overhead-off case; the overhead-on case is roughly 4.5x smaller and still
multi-second.

## Build-state audit: which numbers were measured on which build

Raised by adversarial review: the scx#3618 patch was applied to the submodule
working tree and never committed, so no number in this investigation carried a
provable build state. That is correct and it needed settling before anything
else.

### The discriminator, and why my earlier liveness check was weak

I previously cited "19 `pressure` strings in the binary" as evidence the patch
was live. **That is a bad marker.** Clean, unpatched lavd already contains
`hw_pressure`, `enter_memory_pressure` and `leave_memory_pressure` — a bare
`pressure` count is 7 either way and reads as evidence when it is not. I nearly
compounded this by concluding from a clean rebuild still showing 7 that the
patch could not be detected at all.

The correct discriminator is **`scx_cgroup_bw_pressure`**, a symbol the patch
introduces and clean source does not contain (verified: 0 occurrences in
`lib/cgroup_bw.bpf.c` and `scheds/include/lib/cgroup.h` at `59c30bae`).

`scripts/verify_scx3618_build_state.sh` prints the state of every built
`libscx_lavd.so` from the artifact, and refuses to rely on the source tree or
on memory.

### Current verified state

```
scx source:  59c30bae  0 modified
gitlink:     59c30bae
debug     2026-08-12 19:11:04  unpatched
release   2026-08-12 19:09:40  unpatched
```

### What this does and does not invalidate

**Re-measured on a build verified unpatched at run time**, the noise/overhead
matrix is unchanged:

| overhead | noise CV | worst wait |
|---|---|---|
| off | 0% | 42.18s |
| off | 20% | 42.18s |
| on | 0% | 9.30s |
| on | 20% | 8.80s |

So the overhead-not-noise correction stands on a known-unpatched build.

**The before/after comparison does NOT stand.** Its "unpatched" arm was never
verified from the artifact, and the patched release build has since been
overwritten by a clean rebuild, so the historical state cannot be recovered.
**The byte-identical result must be treated as unproven**, and the review's
simpler explanation — patched-against-patched — is live and was not excluded.
Everything downstream of it is also unproven: the claims that [2/3] and [3/3]
engage but do not help rest on that comparison.

**Redoing it correctly requires** building each arm, running
`verify_scx3618_build_state.sh` immediately before each run, and recording its
output beside the numbers. I did not complete that here.

### Carrying the patch reproducibly

The patch cannot be pinned: its base `3aa52aaf` is not an ancestor of our
`59c30bae`, and the standing rule forbids committing an scx pin that is not an
ancestor of upstream `main`. So it must be carried out-of-pin and applied
explicitly:

```bash
curl -sSL https://github.com/sched-ext/scx/pull/3618.diff -o /tmp/pr3618.diff
cd scx && git apply -3 /tmp/pr3618.diff && cd ../scx-sim
make rebuild-schedulers
./scripts/verify_scx3618_build_state.sh      # must print PATCHED before you trust the run
```
